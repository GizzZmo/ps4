## Background

The PS4 runs a modified **FreeBSD 9** kernel on an **AMD64** CPU. Apple macOS uses the **Mach-O** object format. Because both platforms share the same ISA, a Mach-O binary compiled without any Darwin-specific system calls can be loaded and executed on the PS4 by re-implementing the small piece of kernel logic that normally parses Mach-O load commands.

This PoC demonstrates:
- Parsing `LC_SEGMENT_64` load commands
- Mapping binary segments into anonymous memory
- Resolving the entry point via `LC_MAIN` or `LC_UNIXTHREAD`
- Executing the code after promoting pages to `RX`

## Step 1 — Build the Bare-Metal Mach-O Payload

Build the test payload (`payload.c`) into a Mach-O binary on your development machine. This binary will be embedded in your PS4 payload.

**macOS:**

```bash
clang -target x86_64-apple-macos \
      -static -nostdlib \
      -e __start \
      -o bare_metal_test payload.c
```

**Linux (with osxcross):**

```bash
o64-clang -target x86_64-apple-macos \
          -static -nostdlib \
          -e __start \
          -o bare_metal_test payload.c
```

Verify the output:

```bash
# macOS
otool -l bare_metal_test | grep -E "(LC_SEGMENT_64|LC_MAIN|vmaddr|entryoff)"

# Linux
objdump -p bare_metal_test
```

## Step 2 — Embed the Mach-O Binary in Your PS4 Payload

The simplest approach is to convert the binary to a C byte array using `xxd` or `objcopy`.

### Using `xxd` (macOS / Linux)

```bash
xxd -i bare_metal_test > bare_metal_test_data.h
```

This generates a header like:

```c
unsigned char bare_metal_test[] = {
  0xcf, 0xfa, 0xed, 0xfe, 0x07, 0x00, 0x00, 0x01, …
};
unsigned int bare_metal_test_len = 4096;
```

Include this header in your payload source and pass the array to the loader.

### Using `objcopy` (Linux / PS4 toolchain)

```bash
objcopy --input-target binary \
        --output-target elf64-x86-64 \
        --binary-architecture i386:x86-64 \
        bare_metal_test bare_metal_test.o
```

This creates an object file with three symbols:
- `_binary_bare_metal_test_start`
- `_binary_bare_metal_test_end`
- `_binary_bare_metal_test_size`

Link `bare_metal_test.o` into your payload and reference these symbols in C as:

```c
extern const uint8_t _binary_bare_metal_test_start[];
extern const uint8_t _binary_bare_metal_test_end[];
extern const size_t  _binary_bare_metal_test_size;

size_t payload_size = (size_t)&_binary_bare_metal_test_size;
const uint8_t *payload_data = _binary_bare_metal_test_start;
```

## Step 3 — Compile the Loader for PS4

Compile `macho_loader.c` and `macho_test.c` with the PS4 SDK toolchain. The critical flag is `-DSCE_KERNEL_MPROTECT_AVAILABLE`, which switches the internal `ps4_mprotect` macro from POSIX `mprotect(2)` to `sceKernelMprotect`.

```bash
PS4CC=x86_64-ps4-clang

${PS4CC} -std=c11 -O2 -I. \
    -DSCE_KERNEL_MPROTECT_AVAILABLE \
    -c macho_loader.c -o macho_loader.o

${PS4CC} -std=c11 -O2 -I. \
    -DSCE_KERNEL_MPROTECT_AVAILABLE \
    -c macho_test.c -o macho_test.o
```

Add `macho_loader.o` and `macho_test.o` to your existing payload's link step.

## Step 4 — Wire Up the Loader in Your Payload Entry Point

Inside your PS4 payload's entry point, call `test_macho_execution` with the embedded Mach-O data:

```c
#include "macho_loader.h"

/* Generated by: xxd -i bare_metal_test > bare_metal_test_data.h */
#include "bare_metal_test_data.h"

void payload_main(void) {
    int ok = test_macho_execution(bare_metal_test,
                                  bare_metal_test_len);
    if (ok) {
        /* SUCCESS: Mach-O was loaded and returned 0x1379 */
        notify("Mach-O loader PoC: PASS");
    } else {
        notify("Mach-O loader PoC: FAIL");
    }
}
```

If you need more control (e.g. to inspect the entry-point address or use a different validation value), call `load_mach_o_segments` directly:

```c
#include "macho_loader.h"
#include <sys/mman.h>   /* or PS4 SDK equivalent */

void payload_main(void) {
    void *entry = load_mach_o_segments(bare_metal_test,
                                       bare_metal_test_len);
    if (!entry) {
        notify("load_mach_o_segments failed");
        return;
    }

    /* Promote to RX */
    void  *page      = (void *)((uintptr_t)entry & ~0xfffUL);
    size_t prot_size = (bare_metal_test_len + 0xfff) & ~0xfffUL;
    if (sceKernelMprotect(page, prot_size,
                          VM_PROT_READ | VM_PROT_EXEC) != 0) {
        notify("mprotect failed");
        return;
    }

    __builtin_ia32_mfence();

    typedef int (*entry_fn_t)(void);
    int result = ((entry_fn_t)(uintptr_t)entry)();

    if (result == 0x1379) {
        notify("PASS: 0x1379");
    } else {
        notify("FAIL: unexpected result");
    }
}
```

## Step 5 — Deploy and Test

1. Package your payload as usual (`.bin` / `.elf` / `.prx` depending on your exploit chain).
2. Transfer it to the PS4 via your exploit's delivery mechanism (network socket, USB, etc.).
3. Trigger the exploit and load the payload.
4. Check the on-screen notification (or debug UART output if available) for `PASS` / `FAIL`.

### Diagnostic tips

- If the loader returns `NULL`, double-check that the embedded binary is a valid 64-bit Mach-O (run `file bare_metal_test` on your build machine).
- If `sceKernelMprotect` fails, verify that the kernel exploit has unlocked user-land memory mapping (some exploits require an explicit `mmap` unlock step).
- If the result is wrong (not `0x1379`), inspect the `entryoff` with `otool -l bare_metal_test` and ensure the correct function is at that offset.

## Memory Protection on PS4

The PS4 kernel enforces **DEP (Data Execution Prevention)** — memory mapped with `mmap()` is `RW` only. Attempting to execute `RW` pages will trigger a fault.

`macho_test.c` handles this with the `ps4_mprotect` macro:

```c
/* Compiled with -DSCE_KERNEL_MPROTECT_AVAILABLE: */
sceKernelMprotect(page_base, prot_size, VM_PROT_READ | VM_PROT_EXEC);
```

The sequence is:
1. `mmap()` → `RW` pages (writable, not executable)
2. `memcpy()` → copy code into the `RW` pages
3. `sceKernelMprotect()` → flip to `RX` (executable, not writable)
4. `mfence()` → serialise stores
5. `call entry_addr`

Never skip step 3. Never map pages as `RWX` simultaneously on a production system — this is a security vulnerability.

## Extending the Loader

Once the basic PoC works, the natural next steps are:

### 1. Darwin → FreeBSD Syscall Table

macOS and FreeBSD syscall numbers differ. A shim table translates:

```c
/* macOS write(fd, buf, n) = syscall 4 */
/* FreeBSD write(fd, buf, n) = syscall 4  (same in this case) */
/* macOS exit(code) = syscall 1 */
/* FreeBSD exit(code) = syscall 1 (same) */
/* … but many others differ */
```

Implement a `#UD` (undefined-instruction) trap handler that intercepts `syscall` instructions from the Mach-O payload and routes them through a translation table.

### 2. Dynamic Linker (`dyld`) Emulation

To run payloads that import macOS shared libraries:
- Parse `LC_LOAD_DYLIB` commands.
- Resolve imported symbols against FreeBSD / PS4 equivalents.
- Populate the `__DATA.__got` and `__DATA.__la_symbol_ptr` stubs.

### 3. Objective-C Runtime

For full macOS app compatibility you would need to emulate the Objective-C runtime (`libobjc`). This is significantly more complex and is out of scope for this PoC.
